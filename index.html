Property Wrappers

who owns the data, and who's just borrowing it

@State

A private, small storage box that lives inside one view and survives that view being rebuilt over and over.

In simple terms

SwiftUI redraws your view's body constantly — every tap, every animation frame, it can re-run the whole struct's initializer. Normally that would reset every variable back to its default value each time. @State is SwiftUI's way of saying "remember this value outside the struct's own memory, so it survives those rebuilds." Think of the View struct as a disposable paper form that gets thrown away and reprinted every time something changes — @State is a filing cabinet SwiftUI keeps separately, so the same value shows up on the new form.

When to use

  • Value types only: Int, String, Bool, Double, structs, enums, arrays/dictionaries of these.
  • The data belongs to this view alone — a toggle, a text field's current text, whether a sheet is showing, a loading flag.
  • Never for class instances that other views also need to observe — that's @StateObject's job.
@State private var count = 0
@State private var isShowingSheet = false
@State private var searchText = ""

Where devs get confused

"I set @State in init() and it didn't stick" Setting a @State var from inside a custom init doesn't work the way you'd expect, because @State's storage isn't fully wired up until the view is actually inserted into the hierarchy. If you need to seed a @State value from a parameter, use _property = State(initialValue: ...) inside init, or better — reconsider whether it should be @State at all.
"Why does it reset when I navigate back?" If the parent view creates a fresh instance of the child (e.g. it's inside a List row and the list re-renders, or it's behind an if/else branch that momentarily disappears), a brand-new @State storage box is created too — the old value is gone. @State survives the view's own re-renders, not the view being removed and re-added.

Always mark @State private — it should only ever be set from inside the same view. If a child needs to change it, pass a $binding instead of making the property non-private.

@StateObject vs @ObservedObject

This is the single most confused pair in SwiftUI. Both work with reference types (classes) conforming to ObservableObject. The entire difference is about who is responsible for creating and keeping the object alive.

In simple terms

Imagine a ViewModel class as a whiteboard** that several views can look at. Someone has to be the one who buys the whiteboard and owns it — everyone else just walks up and reads/writes on it. @StateObject is "I am buying this whiteboard, it's mine, I keep it even if my own view redraws." @ObservedObject is "someone handed me a whiteboard, I'll use it, but I am not responsible for its lifetime."

The reason this trips people up: both look and behave almost identically day-to-day (both refresh the view when a @Published property changes). The difference only becomes visible in one specific situation — when the view itself gets recreated by its parent.

@StateObject@ObservedObject
Who creates the objectThis view — you write = SomeClass()Someone else (parent) passes it in
Survives THIS view's body re-renderYesYes
Survives the PARENT recreating this viewYes — SwiftUI protects itNo — a fresh object is created and all state is lost
Correct locationTop of a feature / screen that owns the ViewModelChild views further down that just receive it
// ViewModel
class NewsViewModel: ObservableObject {
    @Published var articles: [Article] = []
    @Published var isLoading = false
}

// Parent — OWNS the view model → StateObject
struct NewsListView: View {
    @StateObject private var viewModel = NewsViewModel()

    var body: some View {
        List(viewModel.articles) { article in
            // pass the SAME instance down → child uses @ObservedObject
            NewsRowView(viewModel: viewModel)
        }
    }
}

// Child — RECEIVES the view model → ObservedObject
struct NewsRowView: View {
    @ObservedObject var viewModel: NewsViewModel
}

Where devs get confused

"My data randomly resets for no reason" Classic cause: you wrote @ObservedObject var viewModel = MyViewModel() at the top of a view (e.g. inside a NavigationLink destination, or a view that's inside a parent's conditional/List). Every time the parent re-renders, SwiftUI re-creates that view struct, which re-runs = MyViewModel() again — brand new object, all your @Published values reset to defaults. The fix is always the same: if you wrote = ClassName(), it must be @StateObject, never @ObservedObject.
"Can I just make everything @StateObject to be safe?" No — if you mark a property @StateObject in a child view that's supposed to receive an existing object from its parent, SwiftUI will actually create a brand-new, disconnected instance rather than using the one you tried to pass in — silently breaking the shared state. The rule is mechanical, not a matter of caution: created here → StateObject. Received as a parameter → ObservedObject.
"Where's the actual 'source of truth' view model created?" Usually one level above where it's first needed — often the screen-level view, or even higher in the App struct with .environmentObject() if many unrelated screens need it (see @EnvironmentObject below).

@Published

Marks a property inside an ObservableObject class so that whenever it changes, every view observing that object (via @StateObject/@ObservedObject/@EnvironmentObject) automatically re-renders.

In simple terms

An ObservableObject by itself does nothing — it's just a class. @Published is what actually broadcasts "hey, I changed" to SwiftUI. Without @Published on a property, changing it will NOT update the UI, even though the class conforms to ObservableObject.

class AuthViewModel: ObservableObject {
    @Published var isLoggedIn = false
    @Published var user: User?
    @Published var errorMessage: String?
    var internalCache: [String: Any] = [:]   // NOT published — UI doesn't care about this
}

Where devs get confused

"I changed a property but the UI didn't update" Almost always means you forgot @Published on that specific property, or you mutated a nested object's property instead of reassigning the whole array/struct (e.g. mutating one property deep inside an array element sometimes doesn't trigger it the way reassigning the array does).
"Should EVERY property be @Published?" No — only ones the UI actually reads. Marking internal bookkeeping properties (like a private cache or a raw network response you've already parsed) as @Published causes extra, wasted view re-renders.

@Environment vs @EnvironmentObject

Different tools that sound similar and get mixed up constantly. One reads small system-provided values. The other injects a whole custom object to an entire screen tree.

@Environment@EnvironmentObject
What it carriesA single system value (color scheme, dismiss action, locale, etc.) or a custom EnvironmentKeyA whole custom class instance (your ViewModel/session/settings object)
Where it comes fromBuilt into SwiftUI, or a key you define yourselfSomething YOU injected higher up with .environmentObject()
Crashes if missing?No — has a default valueYes — app crashes at runtime if never injected
// @Environment — small built-in values
@Environment(\.colorScheme) var colorScheme
@Environment(\.dismiss) var dismiss
Button("Close") { dismiss() }

// @EnvironmentObject — a shared object, injected once
// App entry point
@main
struct MyApp: App {
    @StateObject var session = SessionManager()
    var body: some Scene {
        WindowGroup {
            ContentView()
                .environmentObject(session)   // injected once, available to ALL children
        }
    }
}

// Any child, no matter how deep
struct ProfileView: View {
    @EnvironmentObject var session: SessionManager
}

When to use @EnvironmentObject vs passing @ObservedObject manually

  • Use @EnvironmentObject for truly app-wide/global state needed by many unrelated views — auth session, theme, user settings.
  • Use @ObservedObject passed explicitly through init when only a specific parent → child chain needs it — keeps data flow traceable and easier to test.

Where devs get confused

"Fatal error: No ObservableObject of type X found" This crash means some view declared @EnvironmentObject var x: X but nothing above it in the view hierarchy ever called .environmentObject(x). Common cause: you injected it in the main App scene, but you're previewing a subview in Xcode Previews directly — Previews don't automatically get the App's environment, so you must add .environmentObject(PreviewSessionManager()) to the Preview itself too.
"I injected it but a sibling screen doesn't see it" .environmentObject() only flows downward to that view's children — it must be attached at or above every consumer in the tree, not on a sibling branch.

@Binding

Creates a two-way pipe so a child view can both read AND write a value that's actually owned by a parent (or by a class).

In simple terms

A regular parameter passed to a child view is a one-way copy for value types — if the child changes it, the parent never finds out. @Binding fixes that: rather than passing the value itself, the parent passes a "remote control" (the $-prefixed binding) that reads and writes the parent's actual @State storage.

struct ParentView: View {
    @State private var name = ""
    var body: some View {
        ChildTextField(name: $name)   // $ creates the Binding
    }
}

struct ChildTextField: View {
    @Binding var name: String
    var body: some View {
        TextField("Name", text: $name)
    }
}

Where devs get confused

"Do I need @Binding or just a plain let?" If the child only displays the value → plain let. If the child needs to change a value that the parent owns (a custom toggle, a custom stepper, a custom text field wrapper) → @Binding.
"Can I make up a Binding without real @State behind it?" Yes — Binding(get:set:) lets you construct one manually, useful for transforming a value on the way in/out (e.g. binding a Double to a TextField that only understands String). See the Lists & Forms section for an example.

@ViewBuilder

Lets a function, closure, or computed property return multiple views, or conditionally different views, stitched together — this is literally what makes writing several lines inside body { } legal at all.

In simple terms

Normally, a Swift function can only return ONE type. But your body often contains several Text/Image/Button lines stacked — that only compiles because body is secretly marked @ViewBuilder, and Swift stitches those separate views into one combined "TupleView" behind the scenes. You can add this same power to your own custom functions/containers.

struct CardContainer: View {
    @ViewBuilder let content: Content   // accepts multiple views as a block
    var body: some View {
        VStack { content }
            .padding()
            .background(Color.white)
            .cornerRadius(12)
    }
}

// Usage
CardContainer {
    Text("Title")
    Text("Subtitle")
    Image(systemName: "star")
}

// Conditional views from a helper function
@ViewBuilder
func statusView(isLoading: Bool) -> some View {
    if isLoading { ProgressView() } else { Text("Done") }
}

Where devs get confused

"Cannot convert value of type... to closure result type 'some View'" This error usually means you tried to put an if/else with different view types (or a loose statement) inside a function/closure that ISN'T marked @ViewBuilder. Add @ViewBuilder to the function signature to fix it.

@AppStorage

Reads and writes directly to UserDefaults, and automatically refreshes the view when the stored value changes.

Good for small, simple settings that should survive an app relaunch — theme choice, "has seen onboarding" flag, a saved filter preference. Not meant for large or structured data (use a real persistence layer like SwiftData/CoreData for that, similar to how you built PocketLedger).

@AppStorage("hasSeenOnboarding") var hasSeenOnboarding = false
"I'm storing a whole struct/array and it's acting weird" @AppStorage natively supports simple types (Bool, Int, Double, String, URL, Data). For anything more complex, encode it to Data (JSON) yourself, or better, don't use @AppStorage for it at all.

@FocusState

Tracks and controls which text field / input currently has keyboard focus, and lets you move focus or dismiss the keyboard from code.

enum Field { case email, password }
@FocusState private var focusedField: Field?

TextField("Email", text: $email)
    .focused($focusedField, equals: .email)

focusedField = .email   // sets focus programmatically
focusedField = nil      // dismisses keyboard
Common real use: pressing "return" on the email field should jump focus to the password field — set .onSubmit { focusedField = .password }.

@Namespace

Required for matchedGeometryEffect — the "hero" shared-element animation where one view appears to morph into another across two different view states.

@Namespace private var animation

Image("thumb")
    .matchedGeometryEffect(id: "hero", in: animation)
"The animation just jumps, doesn't smoothly morph" Both the source and destination view must be wrapped in the same @Namespace and the change must happen inside a withAnimation block, and typically one of the two views must be conditionally shown/hidden (not both on screen permanently) for the effect to visibly animate between them.

Passing Data Between Screens / Files

Swift ↔ Swift, Swift ↔ SwiftUI, SwiftUI ↔ SwiftUI — every direction

SwiftUI → SwiftUI, read-only

If the child view only needs to display data and never change it, don't overthink it — pass it as a plain constant through the initializer, exactly like passing an argument to any Swift function.

struct DetailView: View {
    let article: Article
    var body: some View { Text(article.title) }
}
NavigationLink(destination: DetailView(article: selectedArticle)) {
    Text("Open")
}
Common mistakeReaching for @Binding or an ObservableObject here "just in case" adds unnecessary complexity. If it's read-only, a plain let is correct and simplest.

SwiftUI → SwiftUI, child modifies parent's value

Use @Binding (fully explained above). The parent owns an @State value and hands the child a live two-way reference with $value.

Sharing one class instance across many views

Own the object once with @StateObject at the screen that first needs it, then pass the SAME instance down to children as @ObservedObject. If truly global (needed by unrelated tabs/screens), inject with .environmentObject() instead of threading it through every initializer.

Sending data back from a child screen

Three patterns, ordered from simplest to most powerful:

// 1. Binding — simplest, works when both views are alive together in the same hierarchy
@Binding var selectedColor: Color

// 2. Closure callback — great for one-time results, e.g. a picker screen
struct PickerView: View {
    var onSelect: (String) -> Void
    var body: some View { Button("Pick Apple") { onSelect("Apple") } }
}
PickerView(onSelect: { picked in self.fruit = picked })

// 3. Shared ObservableObject — best for async/complex flows
// child updates a @Published property on the shared object,
// parent automatically re-renders because it observes the same object — no explicit "send back" needed
"My closure callback isn't firing" Usually means the child view got dismissed (e.g. sheet closed) before the async work calling the closure finished, or the closure captured a stale/old reference. Double check you're not accidentally capturing self strongly in a way that got deallocated, and that the callback is actually invoked on the path you expect (add a print statement to confirm).

Plain Swift → plain Swift (no UI involved)

This is just ordinary Swift — no property wrappers needed unless the result needs to trigger a UI update somewhere downstream.

struct NetworkService {
    func fetchUser() -> User { /* ... */ }
}
class UserManager {
    var currentUser: User?
    func updateUser(_ user: User) { currentUser = user }
}

Plain Swift file (Model/Service) → SwiftUI View

The Model and Service layers stay plain Swift — no SwiftUI import needed. The ViewModel (an ObservableObject) is the bridge that calls the service, stores results in @Published properties, and the View simply observes the ViewModel. This is the MVVM flow underlying your PocketLedger, Memoize, and Zenith projects.

Model (struct, Codable)
   → Service (plain Swift, fetch/transform data)
        → ViewModel (@Published properties, ObservableObject)
             → View (@StateObject / @ObservedObject, reads @Published)

Unrelated view hierarchies (deep links, tab switches, no shared parent)

Options, in order of preference: @EnvironmentObject injected at the app root (best for most app state); a shared singleton service (.shared) for things like a NetworkMonitor that truly is a single global resource; or, rarely, NotificationCenter, mostly reserved for bridging with older UIKit code.

"Should I just make everything a singleton?" Overusing singletons for app state makes testing and reasoning about data flow harder (any code anywhere can silently mutate global state). Prefer @EnvironmentObject for anything tied to a user session or app-level UI state; reserve true singletons for stateless-ish utilities.

Combine & Async

AnyPublisher, .map, .sink, and when async/await is the better tool

AnyPublisher network call, line by line

This pattern replaces the old completion-handler style (URLSession.shared.dataTask { data, response, error in ... }) with a chain of small, composable transformation steps.

func topHeadlines() -> AnyPublisher {
    return URLSession.shared.dataTaskPublisher(for: request)
        .map(\.data)
        .decode(type: NewsResponse.self, decoder: JSONDecoder())
        .receive(on: DispatchQueue.main)
        .eraseToAnyPublisher()
}
  • dataTaskPublisher(for:) — starts the network call. Emits a (data: Data, response: URLResponse) tuple, or fails with an error.
  • .map(\.data) — shorthand for .map { $0.data }; keeps only the raw Data, discards the URLResponse metadata.
  • .decode(type:decoder:) — feeds the Data through JSONDecoder, turning it into your NewsResponse model. Fails automatically if the JSON doesn't match your Codable struct.
  • .receive(on: DispatchQueue.main) — switches everything downstream to the main thread. Required before touching @Published properties, because UI updates must happen on the main thread.
  • .eraseToAnyPublisher() — hides the long, ugly concrete generic type (something like Publishers.MapError<Publishers.Decode<...>>) behind the simple, stable AnyPublisher<NewsResponse, Error> signature.
"Why erase the type at all — can't I just return the real type?" You technically can, but every time you add/remove/reorder an operator in the chain, the concrete return type changes too, forcing you to update the function signature everywhere it's used. AnyPublisher gives you a stable "public API" so the caller never needs to know or care what's happening internally.

Consuming an AnyPublisher in a ViewModel

private var cancellables = Set()

func loadHeadlines() {
    isLoading = true
    service.topHeadlines()
        .sink(receiveCompletion: { [weak self] completion in
            self?.isLoading = false
            if case .failure(let error) = completion {
                self?.errorMessage = error.localizedDescription
            }
        }, receiveValue: { [weak self] response in
            self?.articles = response.articles
        })
        .store(in: &cancellables)
}
  • .sink has two closures: receiveCompletion fires exactly once, either .finished or .failure(error). receiveValue fires each time a new value arrives (once, for a network call).
  • .store(in: &cancellables) keeps the subscription alive — a Combine subscription is a live object, and if nothing holds a reference to it, it's deallocated (and cancelled) instantly.
  • [weak self] avoids a retain cycle between the closure and the ViewModel, same rule as classic completion handlers.
"My publisher never seems to fire / nothing happens" The #1 cause: forgetting .store(in: &cancellables). Without it, the subscription is deallocated the instant the function returns, before the network call even completes.

.map — general use beyond networking

Transforms each value flowing through the pipeline into something else — conceptually identical to Array.map, just applied to a stream of events over time instead of a fixed collection.

$searchText
    .map { $0.lowercased() }
    .sink { print($0) }

Debounced live search

A very common intermediate Combine pattern — wait for the user to pause typing before actually firing a search, and skip firing again if the text didn't actually change.

$searchQuery
    .debounce(for: .milliseconds(300), scheduler: RunLoop.main)
    .removeDuplicates()
    .sink { [weak self] query in self?.performSearch(query) }
    .store(in: &cancellables)

.assign(to:on:)

An alternative to .sink when you just want to pipe emitted values directly into a property, with no custom logic needed on receipt.

publisher.assign(to: \.articles, on: self)
Gotcha.assign(to:on:) can create a retain cycle since it strongly captures the target — many devs prefer .sink with [weak self] instead, or the newer .assign(to: &$property) syntax when assigning to a @Published property.

.combineLatest

Merges two (or more) publishers, re-emitting a combined value any time EITHER one changes. Useful for form validation that depends on multiple @Published fields at once.

Publishers.CombineLatest($email, $password)
    .map { email, password in !email.isEmpty && password.count >= 8 }
    .assign(to: &$isFormValid)

async/await — the modern alternative

Prefer async/await for simple one-shot calls — no AnyCancellable bookkeeping, reads top-to-bottom like normal code. Prefer Combine for continuous streams: live search debouncing, WebSocket/SSE-style continuous data (relevant to your LivePulse and Memoize projects), or reacting to several @Published values at once.

func topHeadlines() async throws -> NewsResponse {
    let (data, _) = try await URLSession.shared.data(for: request)
    return try JSONDecoder().decode(NewsResponse.self, from: data)
}

// calling it inside a View
.task {
    do { articles = try await service.topHeadlines() }
    catch { errorMessage = error.localizedDescription }
}
Many real codebases mix both: Combine for reactive UI state and debouncing, async/await for straightforward one-off fetches. Neither fully replaces the other.

View Modifiers You Always Forget

the ones that slip your mind mid-build

.onAppear vs .task

Both run code when a view appears, but they behave very differently with async work. .task is structured-concurrency aware: if the view disappears before the async work finishes, the task is automatically cancelled. .onAppear is synchronous-minded and doesn't cancel anything on its own.

.task { await viewModel.load() }       // preferred for async work
.onAppear { print("appeared") }        // fine for simple sync side-effects
"My network call keeps re-firing".onAppear can fire more often than expected (e.g. when a view reappears after a sheet dismisses). If you only want a one-time load, guard with a flag, or use .task which is more predictable for async loading.

.frame

.frame(width: 100, height: 40)
.frame(maxWidth: .infinity, alignment: .leading)

Fixed frame vs maxWidth: .infinity confuses beginners — a fixed frame locks the exact size; maxWidth: .infinity tells the view to expand and fill whatever space is available, which is what you usually want for full-width buttons/rows.

Card-style stack — padding / background / cornerRadius / shadow

.padding(16)
.background(Color(.systemBackground))
.cornerRadius(12)
.shadow(color: .black.opacity(0.08), radius: 8, y: 4)
"My background doesn't include the padding" / "my corner radius looks wrong"Modifier order matters in SwiftUI — each modifier wraps the previous result. Padding must come before background so the background box includes that padding; cornerRadius must come after background so it actually clips the colored box, not just the content inside it.

.overlay + .clipShape (border trick)

.clipShape(RoundedRectangle(cornerRadius: 12))
.overlay(
    RoundedRectangle(cornerRadius: 12)
        .stroke(Color.gray.opacity(0.3), lineWidth: 1)
)

.cornerRadius alone doesn't give you a visible border — you clip the shape, then overlay a stroked copy of the same shape on top to draw the border.

Conditional disabling

Button("Submit") { submit() }
    .disabled(email.isEmpty)
    .opacity(email.isEmpty ? 0.5 : 1)
.disabled() alone doesn't visually communicate anything — always pair it with an opacity or color change so the user can SEE the button is inactive.

.safeAreaInset — sticky bottom bar

ScrollView { content }
    .safeAreaInset(edge: .bottom) {
        Button("Continue") { }.padding()
    }

Better than manually adding padding to the bottom of scroll content — this reserves the space AND keeps the bar pinned above the home indicator/keyboard automatically.

.redacted — skeleton loading state

Text(article.title)
    .redacted(reason: isLoading ? .placeholder : [])

Quick way to show a blurred "skeleton" placeholder instead of building custom shimmering gray boxes by hand.

Navigation & Presentation

sheets, alerts, nav stacks, dismiss

NavigationStack (iOS 16+)

Replaced the older NavigationView. The big advantage: a path array you can manipulate programmatically to push/pop screens from code (deep linking, "go back 3 screens after saving," etc.), not just from user taps.

NavigationStack(path: $path) {
    List(items) { item in
        NavigationLink(item.name, value: item)
    }
    .navigationDestination(for: Item.self) { item in
        DetailView(item: item)
    }
}
// programmatic push
path.append(newItem)
// pop to root
path.removeLast(path.count)

.sheet — bool vs item

.sheet(isPresented: $showSheet) { DetailView() }

// item-based — auto-unwraps an optional, cleaner when the sheet needs specific data
.sheet(item: $selectedArticle) { article in
    DetailView(article: article)
}
"Which one should I use?"If the sheet needs no external data → isPresented. If the sheet displays a specific optional object (e.g. tapping a row opens details for THAT row) → item:, since it avoids a separate bool + separate "currently selected" variable that can get out of sync.

.alert

.alert("Error", isPresented: $showError, presenting: errorMessage) { _ in
    Button("OK", role: .cancel) { }
} message: { message in
    Text(message)
}

Dismissing a sheet from inside

@Environment(\.dismiss) var dismiss
Button("Done") { dismiss() }

TabView

TabView {
    HomeView()
        .tabItem { Label("Home", systemImage: "house") }
    ProfileView()
        .tabItem { Label("Profile", systemImage: "person") }
}

Lists & Forms

ForEach, swipe actions, pickers

ForEach needs Identifiable

struct Article: Identifiable {
    let id = UUID()
    let title: String
}
List(articles) { article in Text(article.title) }
// no Identifiable? use: ForEach(articles, id: \.title)
"Fatal error / weird row glitches when list updates"If your id isn't actually unique/stable (e.g. using array index as id), SwiftUI can misattribute rows during animation/reordering, causing visual glitches. Prefer a real stable UUID.

.swipeActions

.swipeActions(edge: .trailing) {
    Button(role: .destructive) { delete(item) } label: {
        Label("Delete", systemImage: "trash")
    }
}

Picker styles

Picker("Category", selection: $selected) {
    ForEach(categories, id: \.self) { Text($0) }
}
.pickerStyle(.segmented)  // or .menu, .wheel

Form + Section

Form {
    Section("Account") {
        TextField("Email", text: $email)
        SecureField("Password", text: $password)
    }
}

Custom Binding (Binding get/set)

Use when you need to transform a value on the way in and out — the classic example is binding a numeric Double to a TextField, which only understands String.

Binding(
    get: { String(amount) },
    set: { amount = Double($0) ?? 0 }
)

Reads the available size from the parent. Use sparingly — it greedily expands to fill all available space by default, which can throw off your layout if you're not careful.

Animation & Gestures

withAnimation, transitions, taps and drags

withAnimation

withAnimation(.spring(response: 0.4, dampingFraction: 0.7)) {
    isExpanded.toggle()
}
"My change doesn't animate"The state change must happen INSIDE the withAnimation closure. Changing state elsewhere and hoping a nearby withAnimation call catches it won't work.

.transition

if showCard {
    CardView()
        .transition(.move(edge: .bottom).combined(with: .opacity))
}
.transition only animates when the view is being inserted/removed from the hierarchy (e.g. behind an if), not for ordinary property changes — pair it with withAnimation around the state toggle.

Gestures

.gesture(
    DragGesture()
        .onChanged { value in offset = value.translation }
        .onEnded { _ in withAnimation { offset = .zero } }
)
.onTapGesture { print("tapped") }
.onLongPressGesture { print("long pressed") }
